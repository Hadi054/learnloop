What changed in this edition

The first edition set the structure and it holds. This edition changes five things, all of them decided by the learner after reading the first.

  1. The daily unit grew from twenty minutes to an hour. The commitment went up to 15–20 hours a week, so the lesson grew to match.
  2. Four subjects were added that the first edition left out: the design and composition gap, Interface Builder with runtime localization, gRPC over HTTP/2, and the device's sensors. Five new chapters, 38 new lessons.
  3. A language rule was added. The learner reads English as a second language. The rule below says exactly how the writing must sound, and it bans the thing that was making explanations worse rather than better.
  4. A verification tier was added to every lesson. No lesson may be built only from citation. Each one carries at least one number that was actually measured.
  5. Multiple choice was removed from the lesson contract. Every question is now written and self-graded against a model answer. The lesson contract below explains why.

How to use this roadmap

This is not a beginner checklist and not a collection of disconnected courses. Treat it as a dependency graph. Learn enough of each lower layer to explain the upper layer you already use at work.

  1. Start bottom-up with computer systems and operating systems.
  2. Revisit Swift concepts and connect them to memory, compiler, runtime and ABI behaviour.
  3. Revisit UIKit and concurrency with the run loop, scheduler, threads, rendering and isolation in mind.
  4. Add networking, persistence, databases, testing, architecture and performance.
  5. For every topic, write a one-paragraph “under the hood” explanation in your own words.
  6. Prefer small experiments over passive reading when a concept feels abstract.
The rule. Do not ask only “How do I use this API?” Also ask: Who owns the memory? Which thread executes it? What OS service is involved? What compiler or runtime rule makes it work? What happens when it fails?

How the writing sounds

This roadmap and every lesson written from it follow one language rule. It exists because the learner reads English as a second language, and because the first attempt at “making it easier” made it worse.

  • Keep every technical term. retain cycle, mmap, witness table, page fault stay exactly as they are. Renaming a term teaches the wrong word and makes the real documentation unreadable later. The terminology is the syllabus, not an obstacle to it.
  • Simplify the ordinary words around the terms. “the thing that decides”, not “the arbiter”. “runs later”, not “is deferred until such time as”. The hard part was never mmap. It was the sentence mmap was buried in.
  • Short sentences. Twenty-five words on average, thirty-five at the absolute most, one idea per sentence. No semicolon chains.
  • No folksy analogies. Explaining memory by comparing it to a car dealership or a post office teaches the dealership. Then the comparison has to be unlearned, because it breaks at exactly the point where the real behaviour gets interesting.
  • Examples are building examples. Every example is something being constructed: code you would actually write, a screen you would actually ship, a measurement you would actually take.
  • Draw the real machine, not a comparison to one. When a picture is needed, it is a memory diagram, a byte table, or a captured frame dump.

Verification tiers — the gate against trivia

Every lesson is tagged with how its claims were checked.

TierMeaning
EXECRunnable and run. Plain swift, Mac Catalyst, ibtool, command-line tools. The numbers in the lesson were measured, not remembered.
DEVNeeds a real device — permission prompts, the render server, biometrics.
DOCCited convention or documented behaviour that cannot be measured directly.
A lesson that is entirely DOC is a failed lesson. Every lesson must carry at least one measured number. This is the defence against the whole thing decaying into recitable trivia — “minimum touch target? 44 points” is a fact you can hold without understanding anything. The measurement around it is not.

The lesson contract — what fills the hour

REVISED Multiple choice is gone. A four-option question can be passed by recognizing the right shape among the choices, without ever pulling the idea out of memory — exactly the “looks familiar” failure below warns against. Every lesson now has two practice parts. Both are written. Both are graded by rating your own answer against a model answer, the same honesty contract explain-back always used. There is nothing left to guess.
PartMinimum outputTime
ReadUnderstand the terminology, the mechanism, the purpose, the tradeoffs and the common failure modes. Ends with a connection note tracing the lesson up to iOS and down to the machine.~15 min
Questions5–8 open-response questions, mixed types: recall (define a term), reasoning (argue a tradeoff), trace (predict output or state before running anything), debug (find and fix a broken scenario), explain (the whole concept, no notes), apply (use it on a fresh scenario).~25 min
Exercises1–3 focused experiments or small builds, each small enough to isolate one concept. Written without AI. Gate the pass — a lesson cannot be marked done with one left undone.~20 min
Do not grade yourself by recognition. A lesson is not complete because the explanation looks familiar. It is complete when you can retrieve the terminology, predict behaviour, build a small example, debug a failure, and connect it to adjacent layers without relying on AI.

Chapter project contract

  • Combines several lessons from the chapter rather than testing one API in isolation.
  • Contains at least one deliberate failure or debugging task.
  • Requires a short design note explaining decisions and tradeoffs.
  • Uses real tooling where relevant: debugger, Memory Graph, Instruments, network logs, database inspection, tests.
  • Ends with a “trace it downward” explanation connecting the build to lower layers.

Path capstone contract

  • Combines all major chapters in that path.
  • Buildable without following a step-by-step tutorial.
  • Includes tests or verification where appropriate.
  • Includes at least one performance, memory, concurrency or failure analysis.
  • Produces a concise write-up: architecture, mechanisms, tradeoffs, bugs found, and what happens underneath.
Projects and capstones are written with zero AI assistance. That rule is part of the method, not a preference. Reading can be assisted; producing cannot, because the whole point is to find out what you can build without help.

Study method

Because you already build iOS features, the fastest route is not to redo beginner tutorials. Use your existing experience as retrieval cues.

Weekly rhythm at 15–20 hours

  • 6–8 hours — new lessons, at roughly one hour each
  • 3–4 hours — the chapter project in progress
  • 2–3 hours — experiments and debugging on your own code
  • 1–2 hours — scheduled review of earlier lessons
  • 1–2 hours — writing: explain-backs, connection notes, the design note for the current project
Output over consumption. Every week should produce something: a diagram, a small program, a debugging experiment, a one-page explanation, or a refactor. Passive reading hours alone will not build the connections you want.

Spaced review

A lesson passed today comes back tomorrow, then after 3 days, then 7, then 21. A review that goes well moves the lesson up the ladder. A review that goes badly resets it to tomorrow. This is why one concept gets one lesson: a concept folded into another lesson never gets its own place in the schedule, and so never gets reviewed on its own.

Final integrated project

After the ten capstones, build one serious UIKit application without following a tutorial. The app matters less than the requirement that every subsystem forces you to use and explain the layers beneath it.

Required product capabilities

  • Multi-screen navigation with adaptive Auto Layout, reusable list or grid UI, Dynamic Type and VoiceOver.
  • A screen structure built from your own spacing and type scale, with all five screen states handled.
  • An authenticated HTTP API with typed requests and responses, pagination, cancellation, a retry and backoff policy, and meaningful error states.
  • Local persistence plus a two-level cache with explicit invalidation and stale-while-revalidate behaviour.
  • Offline-first first paint: cached data stays usable while revalidation runs.
  • Swift Concurrency: Task, async/await, structured concurrency, @MainActor for UI state, actors and Sendable for shared state.
  • Explicit state with MVVM or a similar presentation pattern, Repository, dependency injection, and Coordinator where useful.
  • Unit tests for business, state and repository behaviour, plus a few meaningful integration tests.
  • Structured logging with enough diagnostics to understand network, persistence, state transitions and failures.
  • At least one performance profiling pass and one memory-leak verification pass.

Deliverables

  • Running app and source code.
  • Architecture diagram and module dependency map.
  • A “request to pixels” trace for one core feature.
  • A “tap to machine” trace covering UIKit, concurrency, threads, memory, network, database and rendering boundaries.
  • The test suite, plus a short statement of what is deliberately not tested.
  • A performance and memory report with real measurements.
  • A failure-mode table: symptom → responsible layer → diagnosis → fix.
  • A retrospective: what you used to do by habit, what you can now explain from first principles, and what gaps remain.
Graduation criterion. You do not need to remember every implementation detail. You should be able to locate a problem in the correct layer, explain the major mechanisms accurately, design an experiment to validate your hypothesis, and read deeper documentation without the terminology feeling disconnected.

Final principle

The goal is not to know every API. The goal is to build a connected model of how software works, so that unfamiliar APIs become easier to understand, debug and evaluate.
